# Aura — Architecture

> Engineering definition. This document describes **how the product is built**: stack, structure, data, and technical rules. For what the product is and how it behaves, see [`idea.md`](idea.md).

## 1. Overview

Aura is a full-stack web application built with Next.js, used on both desktop and mobile. It helps people stay aligned with their mid- and long-term goals and see how their daily activities affect them.

Users enter their data through two modules: a ToDo list (goals and tasks) and a Journal for reflecting on their activities. In return, the server derives goal progress, missed-task feedback cycles with suggested adjustments, and a drift state for each goal. The Home dashboard ("Hoje") combines all of this into a single view, showing whether the user is still moving toward their goals or has drifted.

- **Type:** Full-stack web app
- **Platforms:** Web, with mobile and desktop both first-class (responsive)
- **Main constraints:** solo developer; personal use first, production later; free-tier friendly hosting (Vercel + Neon).

## 2. Tech stack

| Layer                 | Choice                                         | Why                                                                                      |
| --------------------- | ---------------------------------------------- | ---------------------------------------------------------------------------------------- |
| Framework             | Next.js 16 (App Router, Server Components)     | One codebase for UI and server; server actions remove the need for a separate API.       |
| Language              | TypeScript (strict)                            | Business rules are subtle; types catch shape mistakes between DB, domain and UI.         |
| Styling               | Tailwind CSS v4 with CSS-variable design tokens | Tokens map 1:1 to the design; the "Refletir" dark mode is a token swap.                  |
| UI components         | Hand-built primitives (`src/components/ui.tsx`) | The design is bespoke and small; no component library needed.                           |
| State / data fetching | Server Components + Server Actions + `revalidatePath` | Data stays on the server; no client cache to keep in sync.                         |
| Forms / validation    | Zod v4 (`src/lib/schemas.ts`)                  | Same schemas validate every server action input.                                         |
| Database              | PostgreSQL (Docker locally, Neon in production) | Relational data, date types, partial indexes.                                           |
| ORM / query layer     | Drizzle ORM + drizzle-kit migrations           | Typed SQL, plain migrations committed in `drizzle/`.                                     |
| Authentication        | Own session layer: bcrypt + DB sessions + httpOnly cookie | Credentials only; Auth.js credentials can't use DB sessions. ~60 lines, auditable. |
| Hosting / deploy      | Vercel + Neon                                  | Zero-ops, free tiers, Postgres-compatible.                                               |
| Testing               | Vitest (domain rules), Playwright (e2e smoke)  | Rules are pure functions and tested exhaustively; e2e covers the core loop in a browser. |
| Lint / format         | ESLint (next config) + Prettier                | Defaults from the framework.                                                             |

## 4. Conventions

- **Naming:** files kebab-case; components PascalCase; DB columns snake_case (Drizzle maps to camelCase). Routes and UI copy are Portuguese; code, comments and docs are English.
- **Components:** Server Components by default; `"use client"` only for interactivity (checkbox toggles, editors, dialogs). Business logic never lives in components — it lives in `src/domain` (pure) and `src/server` (I/O).
- **Imports / aliases:** `@/*` → `src/*`. Server-only modules import `server-only`. Server Components must not call functions exported from `"use client"` modules (e.g. use `@/lib/cn`, not `cn` from `ui.tsx`).
- **Commits / branches:** feature branches off `main`; small descriptive commits.
- **Error handling:** server actions validate with Zod and return `{ ok: false, error }` with a user-facing Portuguese message; unexpected errors bubble to Next's error boundary.
- **Code that must NOT be written:** no `any`; no queries without a `userId` filter taken from the session; no business rules inside components; no prescriptive/insight text in the UI (see `idea.md` principles).

## 6. Data model

All dates the person reasons about ("today", "this week") are stored as `date` (`LocalDate` strings, `YYYY-MM-DD`) computed in the user's timezone. Timestamps (`timestamptz`) are only for audit/ordering.

### User

`users`: id (uuid), name, email (unique, lowercased), password_hash (bcrypt), birth_date?, timezone (IANA, captured from the browser at sign-up; default `America/Sao_Paulo`), created_at.
`sessions`: id = SHA-256 of the cookie token, user_id, expires_at (30 days).

### Goal

`goals`: id, user_id, title, category?, horizon (`quarterly | monthly | yearly`), created_on (local date), created_at.

### Task

`tasks`: id, user_id, goal_id? (`on delete set null` → becomes an orphan task), title, description?, scheduled_date, time_of_day? (`morning | afternoon | evening`), deadline?, completed_at?, completed_on?, reschedule_count, created_at.

### Missed-task record / Feedback cycle

`feedback_cycles`: id, user_id, task_id, missed_on (day the task was due), opened_on (day the prompt became available), cycle_number, reason? (`no_time | too_tired | lost_motivation | unexpected | other`), reason_text?, suggested_date, suggested_time_of_day?, outcome (`pending | accepted | declined | ignored | auto_applied | resolved`), resolved_on?, created_at.
`resolved` = the person closed the loop themselves (completed the task, rescheduled or unlinked it).

### Journal entry

`journal_entries`: id, user_id, title, body (jsonb: `{kind:"guided", happened, hindered, helps}` or `{kind:"free", text}`), mood? (`good | neutral | low | frustrated | tired`), task_id?, goal_id?, cycle_id?, status (`draft | saved`), entry_date, created_at, updated_at.

### Relationships

User 1—N Goal, Task, FeedbackCycle, JournalEntry, Session. Goal 1—N Task. Task 1—N FeedbackCycle. Task/Goal/FeedbackCycle 1—N JournalEntry (all optional).

### Indexes and constraints

- `tasks (user_id, scheduled_date)`, `tasks (goal_id)`.
- `feedback_cycles` unique `(task_id, missed_on)` (idempotent reconcile), `(user_id, missed_on)`, partial index on pending cycles.
- Deleting a user cascades everything. Deleting a goal orphans its tasks. Deleting a task deletes its cycles and unlinks journal entries.

## 7. Business rules (technical implementation)

| Rule | Where it lives | Notes |
| ---- | -------------- | ----- |
| Goal progress = completed / total linked tasks | `domain/goals.ts#goalProgress` | Computed on read. |
| Soft warning at 6th active task per goal per week | `domain/goals.ts#activeTasksInWeek` + `actions/tasks.ts#saveTask` | Action returns `needsConfirm`; UI offers "Vincular mesmo assim / Salvar sem meta". Never blocks. |
| Task is "missed" (time of day / day / deadline passed) | `domain/missed.ts#missMoment` | Period ends: morning 12:00, afternoon 18:00, evening 22:00, none = end of day; or end of deadline day if earlier. Only goal-linked tasks open cycles. An undone task carries over and can be missed again on later days (max one cycle per day, one pending at a time). |
| Suggested adjustment by reason | `domain/suggest.ts#suggestAdjustment` | default → tomorrow (same period); too_tired → tomorrow morning; unexpected → coming Saturday (next week's if today is Saturday). |
| Ignoring until end of day = declining | `server/reconcile.ts` (lazy) | A pending cycle whose `opened_on` is before today becomes `ignored`. |
| Auto-adjust after 3rd declined cycle (apply last suggestion) | `domain/missed.ts#closesIntoAutoApply` | 3 declined/ignored in a row since the loop was last closed → apply that cycle's suggestion (recomputed if it's already in the past). |
| Drift: 2+ missed milestone tasks in trailing 7 days with at least one unresolved loop | `domain/goals.ts#goalHealth` | Computed on read. Counts distinct tasks. A miss is resolved if it or a later cycle of the same task was accepted/auto-applied/resolved, or the task was completed. |
| Adjustment suggestion only in the live flow | `actions/cycles.ts` | Suggestions are only computed when answering a pending cycle, relative to today. Journal links never produce one. |
| Weeks start on Monday, user's own calendar day | `lib/dates.ts` | `localNow(timezone, now)` → `LocalDate`; all day/week math on plain dates. |

## 8. API / data access

All mutations are Server Actions in `src/server/actions/*`; reads are Server Components calling `src/server/queries.ts`.

| Operation | Method / action | Auth | Notes |
| --------- | --------------- | ---- | ----- |
| Sign up / sign in / sign out | `actions/auth.ts` `signUp`, `signIn`, `signOut` | public / session | Constant-time-ish failure on unknown email. |
| Create / edit / reschedule / unlink task | `actions/tasks.ts#saveTask` | session | Soft-limit confirmation; rescheduling or unlinking resolves a pending cycle. |
| Complete / uncomplete task | `actions/tasks.ts#setTaskDone` | session | Completing resolves a pending cycle. |
| Delete task | `actions/tasks.ts#deleteTask` | session | |
| Create / edit / delete goal | `actions/goals.ts` | session | Delete orphans tasks. |
| Answer missed-task prompt | `actions/cycles.ts#respondToCycle` | session | `accept`, `decline`, `reflect`. |
| Save / delete journal entry | `actions/journal.ts` | session | Drafts autosave; title derived from text when empty. |
| Read views | `queries.ts#loadUserData` (+ `UserData` view builders) | session | One cached load per request. |

## 9. Authentication and authorization

- **Sign up fields:** name, email, password (≥ 8 chars), optional birth date; timezone captured silently.
- **Method:** server-side sessions in Postgres; random 256-bit token in an `httpOnly`, `sameSite=lax`, `secure` (prod) cookie; only its SHA-256 is stored.
- **Password handling:** bcrypt (cost 12) via `bcryptjs`.
- **Per-user data isolation:** every query and action filters by `user_id` from `getAppContext()`/`requireUser()`; ids from the client are always re-checked against the owner (including journal links).
- **Protected routes:** `src/proxy.ts` redirects requests without a session cookie; `requireUser()` in the `(app)` layout and every action is the real check.

## 10. Background jobs / scheduling

None required. `server/reconcile.ts` runs lazily and idempotently at the start of every signed-in request (`getAppContext`): it expires stale prompts (ignored = declined), applies the 3-cycle auto-adjust, and opens prompts for newly missed tasks. If notifications are added later, a Vercel Cron can call the same function per user.

## 11. Environments and configuration

- **Environments:** local (Docker Postgres), production (Vercel + Neon). Preview deployments can point at a Neon branch.
- **Environment variables:** `DATABASE_URL`; `AURA_NOW` (dev only — freezes the clock to test time rules; ignored in production).
- **Secrets handling:** `.env` is git-ignored; `.env.example` documents names only; production values live in Vercel project settings.

## 12. Testing strategy

- **What must be tested:** every rule in section 7 (`src/domain/*.test.ts`, `src/lib/dates.test.ts`), including timezone edges, Saturday-on-Saturday, carry-over misses and the 3rd-cycle auto-apply.
- **Tools:** Vitest (`npm test`), Playwright (`npm run test:e2e`, 390px and 1280px; re-seeds the DB).
- **CI:** TBD — run `npm run lint && npm run typecheck && npm test` on pull requests; e2e needs a Postgres service.

## 13. Performance, accessibility, security

- **Performance targets:** personal-scale data is loaded once per request (`loadUserData`); narrow queries by date range if history grows large.
- **Accessibility:** native `<dialog>` (focus trap, Esc), `role=checkbox/radio` with labels on custom controls, visible focus outline, `aria-current` on navigation. Target WCAG 2.1 AA.
- **Security checklist:** Zod validation on every action; ownership checks on all ids; hashed session tokens; bcrypt; `httpOnly`/`secure` cookies; Server Actions' built-in origin check (CSRF). TODO before public launch: rate limiting on sign-in/sign-up, password reset, account deletion.

## 14. MVP scope

- **In MVP:** the single main flow: sign up → create goal → create task (optionally linked to a goal) → mark complete / miss → failure feedback loop → optional journal reflection → see goal progress and drift on the dashboard.
  - **Accounts:** sign up (name, email, password, optional birth date), sign in, per-user data isolation.
  - **ToDo:** create goals (title, category, horizon) and tasks (date, time of day, deadline); mark complete/incomplete; reschedule; unlink from goal; today / this week / by-goal views.
  - **Goals:** progress (`completed / total linked tasks`), consistency info (misses this week, weeks on track), soft warning at the 6th active task per goal per week.
  - **Failure feedback loop:** missed-task detection, reason (preset or free text), suggested reschedule (default → tomorrow; Too tired → tomorrow morning; Unexpected event → coming Saturday), accept/decline, ignoring = declining, auto-apply after the 3rd declined cycle.
  - **Drift:** on track / drifting state per goal.
  - **Journal:** write entries (title, body, optional mood), browse newest first, filter (all / linked to goals / free), link to a task and/or goal, inbound link from a failed task with pre-filled context.
  - **Home / Dashboard:** today's snapshot, goals overview (progress + drift), recent activity timeline.
  - **Platform:** responsive web, mobile and desktop; weeks start on Monday in the user's own calendar day.
- **Planned, not in MVP:**
  - Manual, retroactive linking of journal entries to existing tasks or goals (shown as a disabled "+ Vincular tarefa ou meta" chip).
  - Viewing all reflections tied to one goal together.
  - Goal indicator showing whether it has accumulated reflection.
  - Drift summary for a drifting goal (most common failure reasons of the month, with a path to related entries and upcoming tasks).
  - Dashboard "Week at a glance": completion rate and journal mood as two separate trends, 7 or 30 days.
  - Dashboard quick actions: add task, write entry, review a drifting goal.
- **Explicitly out of scope:**
  - Weighted goal progress (needs an importance field that doesn't exist yet).
  - Adjustments other than rescheduling (reduce scope, break the task down).
  - Auto-generated insights, causal claims or correlation figures between mood and completion.
  - Sharing, collaboration or any cross-user data visibility.
  - Suggesting adjustments for retroactively linked (past) tasks.
